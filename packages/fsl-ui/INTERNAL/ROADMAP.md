## Program — route to v1

### North star

`fsl-theme` + `fsl-ui` finished to the level where they are the default
choice over Tailwind/Chakra/Material for ttoss applications: semantic,
accessible, AI-first, and visually refined out of the box. **Finished means
in production use — not feature-complete on paper.**

### Scope ruling (2026-07-22)

The program is two packages and one docs section. Everything else is support
tooling, admitted only when it serves the adoption gate.

### The gate (replaces D1 → D2; revised 2026-07-22)

**fsl-ui v1.0 ships when Studio v2 is deployed with its four blocks and the
friction log is worked down to zero blockers.** The blocks (Login,
Settings/CRUD, Dashboard, Pricing) are real application flows in miniature —
they exercise forms+validation, tables+selects, dataviz, and marketing
composition, which is the friction a business app would generate. The
residual self-reference (the system's own showcase validating the system) is
accepted and named: **"first screen in an external business app" is the v1.x
milestone that follows**, not a v1.0 blocker. The AI-executability benchmark
(D1) stays demoted to optional evidence. Rationale: a gate the team never
runs blocks forever; the Studio gate is reachable, in-repo, and generates
representative friction.

    - ✅ **① Button (2026-07-25).** Icon anatomy added using the already-lawful Action roles (`ENTITY_STRUCTURE.Action` = root/control/icon/label — zero taxonomy change, fourth component in a row): `icon={IconIntent}` + `iconPlacement=leading|trailing`, `data-part` root/icon/label, `gap.inline.xs` between glyph and label. Icon-only form = omit `children`; `aria-label` becomes **type-required** (discriminated union, the ADR-001 mechanism) and the control collapses to a square — `sizing.hit` now binds _both_ axes, so the ergonomic floor also supplies the square minimum width (a circle under the pill radius, matching S2) with no new token. `ButtonOwnProps` exported so composites that always show a label (`FormSubmit`) extend the base instead of the icon-only branch. **Follow-ups the owner's review produced, same day:** (a) glyph hosts centre their glyph as a box — `ICON_SLOT_STYLE`, F-022; (b) text-adjacent glyphs size in `em` via the new `sizing.icon.text` step, so ink lands inside the cap-height band (overshoot 0.00 measured); (c) the command's block inset became its own token `spacing.inset.action.block` (bounded 8–9px) so a CTA resolves **exactly 40px** at 1920×1080 while fields stay ~32px — ADR-021 addendum. Deliberate no-changes vs S2, with rationale: **size ramp** (S/M/L/XL) stays rejected — emphasis is carried by `evaluation`, and `hit` is a single floor (ADR-020/CONTRACT §4); **inline padding** stays `inset.control.lg` (≈22px vs S2's 16px — ours breathes wider by choice, and it is a token a theme can retune); **font weight** stays semibold (`text.action`, one theme edit away from bold); **filled border** stays 1px (`outline.control` is our contract; S2 uses 0/2px).
    - ✅ **② ActionButton + ToggleButton realignment (2026-07-25).** `ActionButton` ships in the **utility** silhouette (`radii.control`, `text.label.md`, `inset.control.sm/md` → ~34px) against `Button`'s command silhouette (~40px pill/semibold), and `ToggleButton` moves onto it — a toolbar toggle operates on content, it is not a commitment. Both are Action/root: the pair is a **semantic** distinction (weight of the commitment), not a size variant, so neither gains a `size` prop — the `Meter`/`ProgressBar` precedent for two components sharing an entity and separated by meaning. **Architecture:** the shared anatomy moved into `components/ActionTrigger/anatomy.tsx` — labelling union, glyph slot rules, icon/label parts, the `hit` floor on both axes, the icon-only square, focus ring — parameterised by `COMMAND_SILHOUETTE` / `UTILITY_SILHOUETTE`. `Button`, `ActionButton` and `ToggleButton` now take their geometry from one source, so the drift F-022 fixed cannot re-enter component by component, and the ActionGroup/ActionMenu triggers ahead inherit it for free. `ToggleButton` gained the icon anatomy (icon-only is the common toolbar shape) and its default evaluation moved `primary` → `secondary`. **Theme:** `action.secondary.*.pressed` (consumed only by ToggleButton) inverts to a strong fill — `neutral.700` + `neutral.0` text in light, `neutral.300` + `neutral.900` in dark — because the previous mid-grey read as another hover rather than as ON; it also restores press feedback on an already-engaged toggle. Deferred with evidence: a truly transparent quiet fill (F-024), which `ActionMenu` will force. **Owner question that closed the slice — "is ActionButton the same size as Button? should it be smaller?":** measured at 1920×1080 it is already smaller on four axes (34 vs 40px height, regular vs semibold, 6/12 vs 9/24 inset, `control` vs `action` radius) and identical on one — the **font size**. That parity is deliberate and now enforced: those 34px are the **field row**, byte-identical to `TextField` and `Select` (`sizing.hit` + `inset.control` + `text.label.md`), because a utility trigger exists to stand beside a field. Stepping its type down alone would desynchronise it from the very controls it aligns with, and the reference system draws the same line (one type size per t-shirt size, weight carries the contrast). Guards added: fsl-theme `typography.test.ts` › "trigger contrast" (`text.action.md` and `text.label.md` share a size, differ in weight) and fsl-ui contract invariant #10 › "utility triggers share the field row"; ADR-021 gained the re-litigation answer. **Dark-mode defect found by the same review:** `action.secondary` carried an edge in dark (fill `neutral.700` + border `neutral.500`) where light mode mirrors border to fill — so in dark a secondary action resolved to the _identical_ triple as a text input, and a button was indistinguishable from a field in one mode and clearly distinct in the other. Dark now mirrors the border like light does (`focused`/`expanded` excepted). Also logged: the border-vs-background contrast inventory audits the **base bundle only** — the dark alternate is unaudited, which is the hole that let the divergence in (F-027), and `SearchField` names `data-part="control"` on two nested elements (F-026).
    - ✅ **③ ButtonGroup (2026-07-25).** Structure/root, two props (`orientation`, `align`) and **no `gap`** — the separation between sibling actions is one product-wide decision (`gap.inline.sm`), which is the whole reason it exists over `Stack direction="horizontal"`; both axes read that token, because a row that columnised for space is the same set of actions, not a new stacking rhythm. `horizontal` is **adaptive**: the group measures its children and lays them out in a column when the row does not fit, publishing the rendered axis as `data-orientation` and marking a forced column `data-collapsed="true"`; `vertical` pins the column and skips measurement. Verified in Chromium: collapses at 260px, **recovers** at 700px, light and dark. **The behaviour needs one thing from its children** — grouped triggers stop shrinking, because a trigger's explicit `min-width` (the `hit` floor) overrides a flex item's automatic minimum size and it would otherwise squash below its own label instead of overflowing. Delivered by context (`ActionTriggerGroupProvider` in the shared anatomy), so it reaches a `Button` wrapped in a `Tooltip`; imposed by the _group_, never globally — the same line the reference draws with `flexShrink: { default: 1, isInGroup: 0 }`. Distinct from the three neighbours by design: `Toolbar` is a named region with arrow-key navigation (wrong for a Save/Cancel pair), `DialogActions` reorders by `composition` and is dialog-scoped, `Group` paints a labelled frame. ADR-013 records it, including the trap that the measurement state must be a monotonic pass counter — an `isMeasuring` boolean set `false`-then-`true` in one flush shows React no net change, the re-render is skipped, and the group never collapses.
    - ✅ **④ ActionGroup = `Toolbar`, realigned (2026-07-25).** Reading the reference's source settled what the component is there: its `ActionButtonGroup` is built on React Aria's `Toolbar`, carries **no selection** and paints **no chrome**; selection lives in a separate `ToggleButtonGroup` sharing the same style recipe; and it also ships a bare, unstyled `Toolbar` pass-through. Our `Toolbar` already _was_ that cluster — same entity, same role, same keyboard affordance — so **no component was added**: a second Structure component on `role="toolbar"` differing only in whether it painted would be the duplicate the doctrine rejects (ADR-014). What changed: **the chrome is gone.** Measured in the browser first, which is what decided it — the painted `informational` bar made the component **80px tall around 34px controls**, a card wrapping controls that then read as bare text inside it (the buttons in a bar are `muted`, and ADR-021's ladder gives `muted` no resting edge). Chrome is now composed: `Surface level="overlay"` + `Toolbar` for a floating bar, nothing for a bar on the page. Painting nothing means no colour is evaluated, so the `evaluation` prop is gone (§2.3); it gained `align` (ButtonGroup's vocabulary) and went block-level so `align` has space to act on; re-measured at **32px**, matching `ToggleButtonGroup` exactly. **Family consolidation:** all three group containers now take their arrangement from one shared source — `buildActionGroupStyle` in the trigger anatomy (one gap token, one align mapping, one axis rule) plus the no-shrink context — so the containers cannot drift the way the triggers did before ADR-013. `ToggleButtonGroup` stays `inline-flex` (a segmented control is an object sized by its options; a row and a bar are bands) and now keeps its options from squashing. Deferred with readmission criteria: the reference's `density`/`isJustified` (no consumer), and the adaptive column — a toolbar's overflow answer is an overflow menu, which is exactly ⑤. **Correction the work forced, then corrected again:** the claim "one tab stop with roving focus" was in three places (Toolbar JSDoc, ADR-013's rationale, this ROADMAP) and was read as **false** — `useToolbar` supplies the arrow keys but cannot manage arbitrary children's `tabindex` — so it was removed and a test pinned "every control is still its own tab stop" instead. **Resolved 2026-08-05 (F-028): the claim was right, and the removal answered the wrong question.** `useToolbar` never needs to touch a child's `tabindex` to get one tab stop — on `Tab` it jumps focus itself, via react-aria's generic DOM-walking focus manager (finds tabbable descendants by walking the subtree, no child registration required), to the toolbar's first/last tabbable descendant, then lets the browser's native Tab action carry focus onward from there, out of the toolbar in one step, for _any_ child. The 2026-07-25 test was a false negative: `@testing-library/user-event`'s `tab()` computes the Tab destination from the keydown's original target, not from `document.activeElement` after the toolbar's own handler already moved it, so it can't see the jump. Verified three ways — reading the source, a `fireEvent.keyDown` jsdom test that bypasses user-event's simulation (jumps correctly across a plain host `<button>` and an fsl-ui `Select`), and a real Chromium session via Playwright against Storybook's `KeyboardInvestigation` story (Tab enters once, exits once from any position including Shift+Tab, arrow keys walk every control). No source in `Toolbar.tsx` changed; the docs and tests now say what was already true.

Its single meta is the **trigger** (Action/root, `data-scope="action-menu"` via `ActionButton`'s scope override) because the surface keeps `Menu`'s Overlay identity — two composed identities, not a third invented one. Three things are the component: the glyph is the new **`action.more`** intent (registry grows only when a component needs one), the trigger is the utility icon-only square, and **`aria-label` is required** — the reference defaults it to a translated "More actions", which it can because it ships an i18n runtime; ours cannot, and an English default would ship untranslated copy everywhere (ADR-001). Trigger defaults to `secondary`, matching the reference's non-quiet default, which is why **F-024 did not block this**: the shipped default is correct on every surface. **Second defect, found by opening a menu for the first time since the P3 retune:** `MenuItem` defaulted to `evaluation="primary"`, painting every row a solid `neutral.1000` chip in light and a solid white one in dark — a menu that read as a stack of buttons, live in the Studio's own user menu. Default moved to `muted`, which is not merely quieter but _correct_: its resting background resolves to exactly the popover's colour in both modes, so a row borrows the surface and materialises on hover (contrast 10.4:1 / 13.6:1). ADR-015 records both. **F-024 advanced from "undecided" to "designed":** measured, the quiet rung is wrong on exactly one class of surface and only in dark (`#161616` on a `#262626` card; in light the page and a raised surface are both white, which is why it looked fine) — and the better answer is to **omit** `muted.background.default` rather than add a `transparent` primitive, at the cost of the audit that today proves the quiet ink is legible. **New gap:** a destructive menu row has no way to look destructive — `consequence` carries no colour and `evaluation="negative"` fills the row red, because the Action tree has no "negative ink on a surface" rung (F-029).

## Before deciding anything — read the authorities first (binding)

Added 2026-07-29 because it was earned the hard way. Three "owner decisions"
were escalated during forms C, and reading the design documentation afterwards
showed that **two of the three were already decided in writing** and the theme
already carried the tokens. One friction entry (F-032) was filed claiming a token
was missing that exists. The failure was not analysis — it was not looking.

**The rule: a question about colour, geometry, responsiveness or token grammar is
answered by the design docs before it is reasoned about, and certainly before it
is escalated.** If the docs and a measurement disagree, that is a finding worth
writing down — but the docs are the starting position, not the fallback.

`model.md` §11 already fixes the order when artefacts disagree, and it applies
here too: **FSL Lexicon / Structural Language** (identity and vocabulary) →
**`Types.ts`** (what exists and in what shape) → **family docs** (how to pick in a
real case). Identity beats enforcement beats guidance when the argument is about
meaning; enforcement beats guidance when it is about what exists.

### Two traps this list exists to prevent

- **"The theme lacks a token for X."** Check the theme before filing it. `input.negative.text.default` (`red.700` light / `red.300` dark) exists and is unread; F-032 was filed as a missing token and was really a component reading the wrong role.
- **"The contrast suite will catch it."** It will not, in one direction. `extractTextBackgroundPairs` and `extractBorderBackgroundPairs` both iterate over what exists and `continue` when the counterpart is absent — so **removing** a background silently drops its pairs and the suite stays green. Any change that deletes a colour token owes an explicit replacement assertion.

- **Wave 1 — unblock real apps + fill weak Entities** `~2 wks`: ✅ **COMPLETE
  (2026-07-16).** ToggleButton, ToggleButtonGroup, Tooltip, Popover, Tabs,
  Breadcrumbs, TextArea, SearchField, Separator — all shipped with the

  catalog). Friction logged: ToggleButton (`pressed`≠`active`, inline cascade);
  Tabs (TabPanel is Structure/content, not Navigation); SearchField (Input has
  no `icon`/`closeTrigger` → `leadingAdornment`/`trailingAdornment`). No
  taxonomy changes were needed — every case resolved to an existing role/Entity.
- **Wave 2 — data & forms depth** `~2-3 wks`: ✅ **COMPLETE (2026-07-16).**
  Group, Toolbar, Meter, Disclosure, CheckboxGroup, NumberField, TagGroup,
  ListBox, GridList, Slider, FileTrigger — all shipped with the per-component
  DoD (contract auto-discovery, axe, behavior + keyboard tests, JSDoc,
  catalog). Suite: 1 285 tests green, 100% coverage, build + tsc green.
  **Friction log (FSL D1 validation data):**
  - **ADR-007** — a Collection container may host Selection-pattern items
    (ListBox/GridList: container = Collection/informational, items =
    Selection/input). The entity→ux contract test unions all declared
    entities' contexts, so one file lawfully reads both. No taxonomy change.
  - **ADR-008** — Slider's ROADMAP mapping wanted track→`surface`,
    output→`status`, but Input has neither role. Resolved with internal parts
    (no meta); the FSL §17 widening is **deferred, not proposed** — nothing
    dispatches on those identities (evidence rule). thumb→`control` is legal.
  - **CheckboxGroup / TagGroup / NumberField** — Selection has no
    `description`/`validationMessage`/`closeTrigger` and Input has no `trigger`
    role. Every one resolved to **internal data-parts** (no meta, no legality
    claim) via the RadioGroup-`label` / SearchField-clear-button precedent;
    only lawful roots + items carry metas. Zero taxonomy additions.
  - **TagGroup** shipped the canonical "filter chip → `selected` (not
    `pressed`)" answer into colors.md "Common confusions".
  - **Meter** — RAC's deliberate `role="meter progressbar"` fallback trips
    axe `aria-allowed-attr` (a tooling limitation, not FSL); the correct DOM is
    kept and a per-fixture `axeOptions` disables only that rule for Meter.
  - New Icon intents `action.increment`/`action.decrement` (ADR-005 growth
    rule) for the NumberField steppers.
    Net FSL finding: the flat per-entity vocabulary expressed all 11 components
    without a single taxonomy change — the "missing" roles the ROADMAP part
    lists implied are documentation artifacts, not expressivity gaps.
- **Wave 3 — the heavies** `~3 wks`: ✅ Table (2026-07-22), ✅ ComboBox
