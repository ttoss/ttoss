# Principles

The agentic workflow rests on three pillars. [Get Things Flowing](https://flow.ttoss.dev/docs/method/principles) (GTF) says what holds for any work: the graph is the record, the person decides, review confirms reality. The [product development principles](/docs/product/product-development/principles) say what the work is worth and why flow beats utilization. The [agentic development principles](/docs/ai/agentic-development-principles/overview) say how AI agents behave: context resets, output is probabilistic, and a proxy optimized hard enough stops tracking the goal. The workflow's own principles below combine the three, and they are the only place the workflow cites a pillar. Every rule of the [Delivery Process](./process.md), the [parameters](./parameters.md) and the [routines](./routines.md) rests on one of them, listed under it; a rule page cites a principle only where the reason changes what an agent decides. A rule no principle reaches is a candidate for removal, and so is a principle no rule rests on.

## The graph is the state, and a tick is a function of it

An agent's context ends with its run, so whatever a run does not write outside its conversation is lost ([Compounding Context](/docs/ai/agentic-development-principles/architecture-of-flow#the-principle-of-compounding-context)). The workflow therefore keeps nothing in a conversation: a task's status, what holds it, the changes it references, the assumptions an implementer made and the choices a person answered all live in the [Flow](https://flow.ttoss.dev) graph ([P1](https://flow.ttoss.dev/docs/method/principles#p1-one-source-of-truth-outside-every-head)). A handoff persists what the next run needs, in fields the handoff requires rather than in a message it must infer, and an implementer's assumptions are one of them ([Seam Memory Layer](/docs/ai/agentic-development-principles/architecture-of-flow#the-corollary-of-the-seam-memory-layer), [Externalized Confusion](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-corollary-of-externalized-confusion)). That state is a machine's: each [transition](./process.md#transitions) is a condition read from it and an act with one owner, so a tick is a function from the graph to the graph ([P5](https://flow.ttoss.dev/docs/method/principles#p5-what-to-do-next-is-computed-not-remembered)). It reads, applies every transition that came due, writes and stops, and the next tick does the same from wherever the graph is. A run that dies loses nothing, any agent on any model can run the next one, and context compounds instead of being rebuilt by every run ([Artifact Persistence](/docs/ai/agentic-development-principles/architecture-of-flow#the-corollary-of-artifact-persistence), [Atomic State Isolation](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-corollary-of-atomic-state-isolation)). A parameter points at the file that holds its rule, never a copy, for the same reason, and a signal enters once: an intake looks for the task that already carries the signal's URL before it writes one. Correctness comes from the structure, not from an agent remembering to do the right thing ([Structural Determinism](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-principle-of-structural-determinism)): only a stage's owner moves a task in that stage and, after the verdict, the tick is the only writer ([one owner per transition](./process.md#three-rules), [D9](/docs/product/product-development/principles/achieving-decentralized-control#d9-the-principle-of-boundaries-establish-clear-roles-and-boundaries)), because two writers act on a state the other already changed; a script computes and never writes, so every write stays with a run and the standing decision it acts under; and when nothing schedules a tick, the next run that reads the graph writes what the tick would, since the transition is the graph's, not the scheduler's. A signal from outside enters the same way, as a task the tick delegates like any other, never as a fix the signal starts on its own: capturing is not committing ([P3](https://flow.ttoss.dev/docs/method/principles#p3-capturing-is-not-committing)), and what enters execution is the tick's decision ([Admission Control](/docs/ai/agentic-development-principles/economics-of-interaction#the-corollary-of-admission-control)). The pace belongs to whatever schedules the ticks, not to the agents, and what a run did not write did not happen.

Rules that rest on it:

- One owner per transition.
- With no tick, the next run that reads the graph writes what the tick would.
- A script never writes; every write stays with a run, under the standing decision.
- A parameter is a pointer to the file that holds it, never a copy.
- The implementer records its assumptions at the handoff.
- Intake writes a task, never a fix, and looks for the task the signal's URL already names before it writes one.

## One engine, extended for any project

The states, stages, owners and transitions are the same for every project. A project extends them only at defined [extension points](./parameters.md#extension-points): an extension answers a question the engine asks and never changes the engine, and a point left empty takes its default. Shared handoffs keep the cost of a new project or a new agent flat instead of growing with every pair ([Protocol Standardization](/docs/ai/agentic-development-principles/protocol-of-communication#the-principle-of-protocol-standardization)). A rule lives at the most general level where it holds, [Get Things Flowing](https://flow.ttoss.dev/docs/method/principles) for any work, this workflow for software delivery, the [ttoss skills](https://github.com/ttoss/skills) for how an agent carries it out and the parameters for one product, and a rule found true in every project moves up ([Curated Minimalism](/docs/ai/agentic-development-principles/architecture-of-flow#the-corollary-of-curated-minimalism)). The model a parameter names is part of what the engine runs on, so it is pinned by exact id and an upgrade is a migration, never a swap an alias makes under a project without a change anyone made ([Pinned Substrate Migration](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-corollary-of-pinned-substrate-migration)). The process names acts, never tools, so it reads the same on any code host and for a delivery that is not code; a stage a project answers with none is skipped, not replaced; and the parameters bind every session working in the repo, a person's included, because an engine two kinds of worker run differently is two engines. So any project, delivering code or [anything else](./process.md#delivery-kinds), adopts the workflow by answering its parameters, and an improvement to the engine reaches every project at its next run.

Rules that rest on it:

- A project extends the engine only at its extension points, and never changes it.
- The process names acts, never tools.
- A stage answered with none is skipped.
- The parameters bind every session working in the repo, not only the agents'.
- Models by exact id.

## The author never verifies its own work

An agent that judges its own change optimizes the check instead of the goal ([Proxy Collapse](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-principle-of-proxy-collapse)). The reviewer runs in a fresh context, did not write the change and never fixes it, which is the one isolation worth the continuity it costs ([Verifier Sovereignty](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-corollary-of-verifier-sovereignty), [Boundary Justification](/docs/ai/agentic-development-principles/architecture-of-flow#the-corollary-of-boundary-justification)); a change to the gates that judge it waits on a person; a verdict is a status on the commit it judged, from an identity allowed to give it, because an agent cannot tell an instruction from the data it reads, so a verdict it read in a comment is not one ([Instruction-Data Conflation](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-principle-of-instruction-data-conflation)). Fix rounds have a limit, since each round on the same gates compounds the error of the last and takes the system out of the range where more effort helps ([Compounding Contextual Error](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-corollary-of-compounding-contextual-error), [V13](/docs/product/product-development/principles/exploiting-variability#v13-the-nonlinearity-principle-operate-in-the-linear-range-of-system-performance)). And a task closes only on its effect observed where it matters, never on green checks ([P6](https://flow.ttoss.dev/docs/method/principles#p6-the-record-is-an-estimate-review-confirms-reality), [Intrinsic Verification](/docs/ai/agentic-development-principles/governance-of-technical-debt#the-corollary-of-intrinsic-verification)), as soon as it can be seen, because what a reversal must unwind grows with every hour between commitment and detection ([Detection Window](/docs/ai/agentic-development-principles/economics-of-interaction#the-corollary-of-the-detection-window)). An investigation is held to the same: it delivers knowledge, and closes with the evidence it found as its outcome, never with the fact that it ran.

Rules that rest on it:

- Rounds have a limit.
- The reviewer did not write the change and never fixes it.
- The agents integrate; a change to its own gates waits on a person.
- A verdict is a status on the commit it judged, from an identity allowed to give it, and the code host requires it.
- A task closes on an effect observed where it matters.
- An investigation closes with its evidence as its outcome.

## Autonomy is bounded by reversibility

Agents act alone where an act can be undone and its failure is seen in time; a person decides the rest ([P2](https://flow.ttoss.dev/docs/method/principles#p2-the-person-decides-the-agent-proposes), [Reversibility-Bounded Autonomy](/docs/ai/agentic-development-principles/governance-of-agency#the-corollary-of-reversibility-bounded-autonomy)). Both cut what a wrong act costs rather than how often one happens, the cheaper lever when output is probabilistic ([V12](/docs/product/product-development/principles/exploiting-variability#v12-the-principle-of-variability-consequence-reducing-consequences-is-usually-the-best-way-to-reduce-the-cost-of-variability)): a change carries its reversal path, designed in before it integrates, when buying it is cheapest ([Designed Reversal](/docs/ai/agentic-development-principles/economics-of-interaction#the-corollary-of-designed-reversal)), it goes up green from automated loops that correct it before a person is asked ([Verification Latency](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-corollary-of-verification-latency)), and one that proves harmful is reverted by that path before the fix is attempted, a cheap variability accepted to hold the expensive one ([V14](/docs/product/product-development/principles/exploiting-variability#v14-the-principle-of-variability-substitution-substitute-cheap-variability-for-expensive-variability), [F17](/docs/product/product-development/principles/controlling-flow-under-uncertainty#f17-the-wsjf-scheduling-principle-when-job-durations-and-delay-costs-are-not-homogeneous-use-wsjf)). A standing decision delegates what agents may do, so the many small choices are made by rule instead of by queueing for a person, and every write made under it names it as its cause ([P4](https://flow.ttoss.dev/docs/method/principles#p4-every-change-to-a-commitment-carries-its-cause), [E13](/docs/product/product-development/principles/economic-view#e13-the-first-decision-rule-principle-use-decision-rules-to-decentralize-economic-control)); an answer a person gave more than once to the same kind of choice was meant as such a rule, so the Audit proposes it as one, and the person's word stays the rule. What is reserved to a person is what no later tick undoes or what only they can own, product intent, security, auth, billing, data loss, migrations, public contracts, their agents' instructions, and a delivery whose act reaches outside the product; and a change closed without integrating goes back to a person, to implement again or to cancel, because closing it was somebody's decision the tick cannot read. A choice nobody delegated waits on who decides, written in the graph rather than guessed ([Silent Interpretation](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-principle-of-silent-interpretation)), and only after the tests that show it is a choice at all, since a choice loses value while it waits, and the tests rank what lasts, enforced by the system over context over procedure over prose, because the deeper a control sits the less what an agent reads can outvote it ([E10](/docs/product/product-development/principles/economic-view#e10-the-first-perishability-principle-many-economic-choices-are-more-valuable-when-made-quickly)). The code host, not an instruction, enforces the merge rule ([Deterministic Enforcement Supremacy](/docs/ai/agentic-development-principles/foundations-of-hybrid-allocation#the-corollary-of-deterministic-enforcement-supremacy)), and an instruction changes only through a person's merge, because a prompt is a shallow control that what it reads can outvote ([Control Stack](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-corollary-of-the-control-stack)): a gate nobody can show passed has not passed, since merging is the act no later tick undoes ([Asymmetric Risk](/docs/ai/agentic-development-principles/governance-of-agency#the-principle-of-asymmetric-risk)). Another agent's work is not an agent's to take: a run holding a task past its stale limit is left and reported, never reclaimed ([P7](https://flow.ttoss.dev/docs/method/principles#p7-report-dont-refuse-reconcile-explicitly)).

Rules that rest on it:

- A choice goes to a person only after a test, and the long-term test ranks durability: enforced, then context, then procedure, then prose.
- Product intent, security, auth, billing, data loss, migrations, public contracts and the agents' instructions are a person's; so is a delivery that reaches outside the product.
- The change closed without integrating goes to a person: implement it again, or cancel it.
- A check that needs a target the project did not name waits on a person.
- The change goes up green, with its reversal path.
- An integration that proves harmful is reverted by that path before the fix.
- The code host enforces the merge rule; instructions change only through a person's merge.
- A gate fails closed: no verdict for the head, or a `Review` the parameters do not state, never reads as passed.
- Another agent's run holding a task past `Stale after` is left, and reported.
- The Audit proposes a standing rule from an answer a person gave more than once.

## Cost of delay orders the work, read from a proxy nobody estimates

Work is ordered by what waiting costs, never by who asked first or by size ([F16](/docs/product/product-development/principles/controlling-flow-under-uncertainty#f16-the-hdcf-scheduling-principle-when-job-durations-are-homogeneous-do-the-high-cost-of-delay-job-first), [E5](/docs/product/product-development/principles/economic-view#e5-the-inactivity-principle-watch-the-work-product-not-the-worker)). Nobody quantifies that cost per task, and an agent asked to would invent a number and then optimize it ([Silent Interpretation](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-principle-of-silent-interpretation), [Proxy Collapse](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-principle-of-proxy-collapse)), so the workflow reads it from a fixed proxy, the same for every project: the [stage](./process.md#three-rules) the work is in, since a defect in production hurts every hour, an open change gathers conflicts, integrated work nobody has seen in effect lets a regression run, and new work loses little by waiting a tick; and the two words a person may add: a `very_high` priority, which is their own assertion that waiting costs most, whatever the stage, and the `bug` tag, which at `high` says the defect is already in effect ([P2](https://flow.ttoss.dev/docs/method/principles#p2-the-person-decides-the-agent-proposes)). The proxy is the economics, coarsened: the order of the stages is their cost of delay ranked once for every project, which prevents the large mistakes without the per-task precision nobody has ([E1](/docs/product/product-development/principles/economic-view#e1-the-principle-of-quantified-overall-economics-select-actions-based-on-quantified-overall-economic-impact), [FF2](/docs/product/product-development/principles/using-fast-feedback#ff2-the-principle-of-efficient-control-control-parameters-that-are-both-influential-and-efficient)). Below the proxy, Flow's ranking, priority then leverage ([P5](https://flow.ttoss.dev/docs/method/principles#p5-what-to-do-next-is-computed-not-remembered)), orders the work inside a stage and never across them, since a priority holds only where the work is waiting ([F18](/docs/product/product-development/principles/controlling-flow-under-uncertainty#f18-the-local-priority-principle-priorities-are-inherently-local)). A brief asking for several deliveries is split before it is started, because a large batch delays everything it carries ([B1](/docs/product/product-development/principles/reducing-batch-size#b1-the-batch-size-queueing-principle-reducing-batch-size-reduces-cycle-time)) and an agent delivers what it can hold whole ([Problem Decomposition](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-corollary-of-problem-decomposition)), and the Chase reports its sections in the same order, so a person reads first what their delay costs most.

Rules that rest on it:

- What ages fastest goes first, read from the stage, a `very_high` priority and a `high` bug.
- A brief asking for several deliveries is split.
- The Chase's sections come in the order of what ages fastest.

## A person's attention is the critical queue

Agents add work faster than people answer it, so the queue that costs most is the one only a person can drain: a decision, a review, a merge reserved to them ([W21](/docs/product/product-development/principles/applying-wip-constraints#w21-the-principle-of-the-critical-queue-constrain-wip-in-the-section-of-the-system-where-the-queue-is-most-expensive), [FF24](/docs/product/product-development/principles/using-fast-feedback#ff24-the-attention-principle-time-counts-more-than-money)). Reviewing and validating what agents built is where that queue grows with every implementation, so the tick holds new work upstream, where waiting is cheap ([V16](/docs/product/product-development/principles/exploiting-variability#v16-the-principle-of-variability-displacement-move-variability-to-the-process-stage-where-its-cost-is-lowest)), once the [review queue](./parameters.md#runtime) is full: the changes waiting to be reviewed, integrated by a person or seen in effect by one. A child ends at its handoff, so the run cap alone leaves that queue unbounded ([W1](/docs/product/product-development/principles/applying-wip-constraints#w1-the-principle-of-wip-constraints-constrain-wip-to-control-cycle-time-and-flow), [W21](/docs/product/product-development/principles/applying-wip-constraints#w21-the-principle-of-the-critical-queue-constrain-wip-in-the-section-of-the-system-where-the-queue-is-most-expensive)); the cap still holds, and a child that outlives its slice is closed, because a run's duration is unknown and may be unbounded ([F19](/docs/product/product-development/principles/controlling-flow-under-uncertainty#f19-the-round-robin-principle-when-task-duration-is-unknown-share-time-among-tasks)). Decisions stay out of it: a decision holds only the work it blocks, so a thousand open choices never stop the work nobody has to choose about. Only new work waits: integrating, releases, checks, rounds and what a person marked urgent go on, so the queue keeps draining. The limit reads the queue's size, which reacts at once, never its cycle time, which reacts only once the work leaves ([Q13](/docs/product/product-development/principles/managing-queues#q13-the-first-queue-size-control-principle-dont-control-capacity-utilization-control-queue-size), [Q14](/docs/product/product-development/principles/managing-queues#q14-the-second-queue-size-control-principle-dont-control-cycle-time-control-queue-size)), and the Chase puts the person queue first and shows each person's arrivals against their departures, and a wait that names nobody is addressed to the project's admins, since nothing else reaches anyone for it; a review request nobody picked up within `Review grace` falls to the `Review` fallback rather than holding the change, because a queue left alone does not correct itself ([Q16](/docs/product/product-development/principles/managing-queues#q16-the-intervention-principle-we-cannot-rely-on-randomness-to-correct-a-random-queue)) and more agents or tasks will not help.

Rules that rest on it:

- Child runs are capped; a stale one is closed.
- New work waits upstream once the review queue is full; decisions do not count, and only new work waits.
- The person queue comes first, and growing two weeks running opens the digest.
- A wait that names nobody is addressed to the project's admins.
- A review request lost past `Review grace` falls to the `Review` fallback.

## A number is Flow's answer, never an agent's estimate

The graph reaches nobody who does not read it, so the routines carry it to people: the Chase tells each person what the graph holds for them, because knowledge that stays in the graph serves the agents and not the people it waits on ([Contextual Readiness](/docs/ai/agentic-development-principles/architecture-of-flow#the-corollary-of-contextual-readiness)). What it reports is what the work product does, never what a worker does ([E5](/docs/product/product-development/principles/economic-view#e5-the-inactivity-principle-watch-the-work-product-not-the-worker)): each state's arrivals, departures and age, the cumulative flow that shows a queue as it forms ([Q11](/docs/product/product-development/principles/managing-queues#q11-the-cumulative-flow-principle-use-cfds-to-monitor-queues)); rework after the check and failure demand, the leading indicators of what the next weeks will cost ([FF3](/docs/product/product-development/principles/using-fast-feedback#ff3-the-principle-of-leading-indicators-select-control-variables-that-predict-future-system-behavior)); and, from the Audit, spend on work that did not ship, what became of incubated work and the untriaged inbox, the inventory that is invisible unless something counts it and the expansion nothing else stops ([E1](/docs/product/product-development/principles/economic-view#e1-the-principle-of-quantified-overall-economics-select-actions-based-on-quantified-overall-economic-impact), [Q1](/docs/product/product-development/principles/managing-queues#q1-the-principle-of-invisible-inventory-product-development-inventory-is-physically-and-financially-invisible), [W20](/docs/product/product-development/principles/applying-wip-constraints#w20-the-expansion-control-principle-prevent-uncontrolled-expansion-of-work)). Every number is written as Flow answers it, never a ratio, a goal or a threshold, because a number aimed at is a number reached while the work it stood for stops ([Proxy Collapse](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-principle-of-proxy-collapse)). The arithmetic behind each is a script over Flow's answers, never an agent's: counting is a well-structured problem, and a sum an agent works out is a guess that reads like a fact ([Problem Structure Allocation](/docs/ai/agentic-development-principles/foundations-of-hybrid-allocation#the-principle-of-problem-structure-allocation), [Structural Determinism](/docs/ai/agentic-development-principles/physics-of-ai-integration#the-principle-of-structural-determinism)).

Rules that rest on it:

- The Chase tells people what the graph holds for them.
- The Chase reports each state's arrivals, departures and age, as Flow answers them.
- The Chase reports rework after the check, and failure demand.
- The Audit reads spend on work that did not ship, incubated exits and the inbox.
- Health numbers are written as Flow answers them: no ratio, no goal, no threshold.
- The routines' arithmetic is computed by scripts from Flow's answers, never by an agent.

## Every run is paid for

A run looks free to the agent that starts it and is not: every prompt costs money, latency and a share of what the people downstream will read ([Prompt Economics](/docs/ai/agentic-development-principles/economics-of-interaction#the-principle-of-prompt-economics)), so the Audit measures what runs spend, from the instruction files every session loads and the runs Flow records, and a routine is as cheap as its question allows. It runs on the cheapest model that does the work, because intelligence spent on a low-entropy task is bought and wasted ([Allocative Efficiency](/docs/ai/agentic-development-principles/economics-of-interaction#the-principle-of-allocative-efficiency)), loads only the tools it calls, and hands a wide read to a subagent that returns the conclusion. The routines run on cadences, hourly, daily and weekly, because a regular rhythm turns unpredictable events into predictable ones ([F5](/docs/product/product-development/principles/controlling-flow-under-uncertainty#f5-the-principle-of-periodic-resynchronization-use-a-regular-cadence-to-limit-the-accumulation-of-variance)), and the cadences nest as multiples of one another, so the week's Audit reads the days the Chase reported and the hours the tick ran ([F14](/docs/product/product-development/principles/controlling-flow-under-uncertainty#f14-the-harmonic-principle-make-nested-cadences-harmonic-multiples)).

Rules that rest on it:

- Routines run on nested cadences, on the cheapest model that does the work.
- A routine loads only the tools it calls, and hands a wide read to a subagent.
- The Audit measures what runs spend.
